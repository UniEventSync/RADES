################################################################################
## Project Description
################################################################################

RADES (Responsive Application for Digital Event System) is a responsive,
browser-based campus event management and ticketing platform for IBA Karachi.
It centralises the full lifecycle of a campus event: creation by student
societies, discovery by students, solo and team registration, paid ticketing
(Stripe Test Mode only), unique QR-code tickets, QR-based attendance check-in,
email notifications, Google Calendar integration, institutional oversight,
analytics and post-event feedback.

Today, event information is scattered across chat groups and posters, and
registration / attendance is handled with separate tools or by hand. RADES
replaces that with one platform used by four kinds of people:

  - Students            : browse, register, pay, hold QR tickets, give feedback
  - Society Admins      : student panel members who create events, scan
                          tickets, view analytics, manage the society panel
  - Student Societies Office (Office of Student Societies and International
    Engagement)         : read-only cross-society oversight
  - Faculty Advisors    : associated with events, can view event information

The product is a responsive web application (NOT a native app). Every core
workflow must work equivalently on desktop and mobile browsers.

The visual identity is: clean, light, professional. White cards on a soft
grey-blue page, one confident blue primary colour, generous whitespace,
readable type, gentle rounded corners and subtle shadows. Motion is calm and
functional — it reveals content, confirms an action, or shows state. Nothing
is decorative noise. NO GRADIENTS — every colour is a solid hex.

HARD RULES (apply to the entire project):
  1. FREE SERVICES ONLY. Every service used must have a free tier sufficient
     for a semester project (Supabase Free, Vercel Hobby, Resend Free,
     Stripe Test Mode, Google Cloud free APIs, GitHub). No paid plan, no
     credit card required for any service other than Stripe account
     creation in Test Mode.
  2. PAYMENTS = STRIPE TEST MODE ONLY. No live keys anywhere, ever. Test keys
     (sk_test_ / pk_test_) only. The UI shows a visible "TEST MODE" badge on
     every checkout and refund view.
  3. LOGIN IS RESTRICTED BY EMAIL PATTERN (see "Authentication & Access Rules").
     Nobody whose email does not match is able to create or use an account.
  4. AUTHORISATION IS ENFORCED SERVER-SIDE AND IN THE DATABASE (Supabase RLS).
     Hiding a button in the UI is never treated as security.
  5. No raw card data ever touches RADES. Stripe-hosted Checkout handles it.

## Authentication & Access Rules
################################################################################

------------------------------------------------------------------------
Allowed Email Patterns (the ONLY way to sign up or sign in)
------------------------------------------------------------------------

  STUDENTS  :  [Firstname].[Secondname].[ERP]@khi.iba.edu.pk
               e.g.  ayesha.khan.12345@khi.iba.edu.pk
               Regex (case-insensitive):
                 /^[a-z]+\.[a-z]+\.\d{5}@khi\.iba\.edu\.pk$/i
               ERP = 5-digit numeric ERP number. The digit count lives in one
               constant so it can be changed in one place.

  TEACHERS  :  [name]@iba.edu.pk
               e.g.  saraahmed@iba.edu.pk  or  sahmed@iba.edu.pk
               Regex (case-insensitive):
                 /^(\.[a-z0-9]+)*@iba\.edu\.pk$/i

  Anything else (gmail.com, other domains, malformed local part) is rejected.

  All regexes and the ERP length live in ONE file: src/lib/auth/email-rules.ts
  and are imported by the client form, the server route and the tests.

------------------------------------------------------------------------
Where the rule is enforced (defence in depth — all three layers required)
------------------------------------------------------------------------

  1. Client  : react-hook-form + zod schema shows an instant, understandable
               message ("Use your IBA student email: firstname.lastname.ERP
               @khi.iba.edu.pk").
  2. Server  : /api/auth/signup route re-validates with the same zod schema
               before calling Supabase Auth.
  3. Database: a Postgres trigger (BEFORE INSERT on auth.users) raises an
               exception if the email does not match either pattern, so even a
               direct call to the Supabase Auth API cannot create an
               ineligible account.

------------------------------------------------------------------------
Derived data at sign-up
------------------------------------------------------------------------

  From the email the system derives (and stores in profiles):
    - account_type : 'student' | 'faculty'
    - first_name, last_name (students: from the local part)
    - erp_number   (students only)
  Email verification is REQUIRED before first sign-in (Supabase confirmation
  link). An unverified account cannot reach any protected page.

------------------------------------------------------------------------
Roles
------------------------------------------------------------------------

  student            — default for @khi.iba.edu.pk accounts
  faculty            — default for @iba.edu.pk accounts; may be associated as
                       Faculty Advisor on events
  society_admin      — NOT a global role. Granted per society through the
                       society_members table (a student can be admin of one
                       or more societies). Enables event management for that
                       society only.
  office             — Student Societies Office oversight. Assigned manually in
                       the database for specific @iba.edu.pk accounts. Never
                       self-assignable.
  super_admin        — Developer-only maintenance role (seed/data fixes).

## Tech Stack
################################################################################

------------------------------------------------------------------------
Core Framework
------------------------------------------------------------------------

  - Next.js (latest stable, App Router) — server components by default,
    client components only where interactivity is required
  - TypeScript — strict mode, all components, hooks and API routes typed
  - Route Handlers (src/app/api/**) for all security-sensitive business logic
  - next/font (Google Fonts, self-hosted at build time) and next/image

Styling
------------------------------------------------------------------------

  - Tailwind CSS v4 — utility-first, design tokens declared in globals.css

  - shadcn/ui (copy-in components built on Radix UI primitives) for Dialog,

  - lucide-react for icons
  - No CSS-in-JS, no CSS modules, no extra UI kit

------------------------------------------------------------------------
Animation
------------------------------------------------------------------------

  - Motion (motion.dev) — the ONLY animation library. Imported as:
      import { motion, AnimatePresence } from 'motion/react'
  - Used for: entrance fades, list staggers, modal / sheet transitions,
    button feedback, tab content swaps, success confirmations
  - All animations animate transform and opacity only
  - Every animation respects prefers-reduced-motion (disabled / minimal)

------------------------------------------------------------------------
Backend-as-a-Service (Supabase Free Tier)
------------------------------------------------------------------------

  - Supabase Auth       : email + password, email verification, password reset
  - Supabase PostgreSQL : all application data
  - Row Level Security  : authorisation at database level on EVERY table
  - Supabase Storage    : event images, society logos (public buckets with
                          upload policies limited to authorised admins)
  - @supabase/supabase-js and @supabase/ssr (cookie-based sessions for the
    App Router)
  - Postgres functions (RPC) for atomic operations: register_for_event,
    check_in_ticket, cancel_event
  - Note: Supabase Free pauses inactive projects after a week. Keep a weekly
    health ping or open the dashboard before demos.

------------------------------------------------------------------------
Payments (Stripe — TEST MODE ONLY)
------------------------------------------------------------------------

  - stripe (Node SDK, server-side only)
  - Stripe-hosted Checkout (redirect flow) — no card fields in our UI
  - Webhook endpoint: POST /api/stripe/webhook (signature verified with
    STRIPE_WEBHOOK_SECRET)
  - Events handled: checkout.session.completed,
    checkout.session.expired, charge.refunded, refund.updated
  - Refunds created through the Stripe Refunds API on event cancellation
  - Idempotency: Stripe event.id stored in processed_stripe_events; every
    handler is safe to re-run
  - Local development: Stripe CLI (`stripe listen --forward-to
    localhost:3000/api/stripe/webhook`) — free
  - Test card for demos: 4242 4242 4242 4242, any future expiry, any CVC.
    Failure card: 4000 0000 0000 0002.

------------------------------------------------------------------------
Email (Resend — Free Tier)
------------------------------------------------------------------------

  - resend (Node SDK, server-side only)
  - Free tier limits: 100 emails/day, 3,000/month — sufficient for the project
  - Templates written as React Email components (@react-email/components)
  - IMPORTANT: Resend only delivers to arbitrary recipients from a verified
    sender domain. Using the shared onboarding@resend.dev sender delivers only
    to the account owner's own address. If no domain is available, the
    documented free fallback is Nodemailer + a Gmail SMTP app password
    (500/day) behind the same sendEmail() interface in src/lib/email/send.ts,
    so the provider can be swapped by changing one file and one env variable.
  - Supabase's own auth emails (verification, password reset) are routed via
    Resend SMTP in the Supabase dashboard (Auth → SMTP settings) because the
    built-in Supabase mailer is heavily rate limited on the free tier.

------------------------------------------------------------------------
Calendar (Google Calendar API — Free)
------------------------------------------------------------------------

  - Google Cloud project, OAuth 2.0 Web client, scope:
      https://www.googleapis.com/auth/calendar.events
  - Google Identity Services (token client) in the browser to get a short-lived
    access token ONLY when the student clicks "Add to Google Calendar"
    (incremental authorisation; Google is never used to log in)
  - Event created through POST /api/calendar/add, which calls the Calendar
    REST API (events.insert) using the user's access token. Tokens are NOT
    stored.
  - OAuth consent screen kept in "Testing" status: up to 100 listed test users,
    no Google verification required. Add demo accounts as test users.
  - Fallback shown beside the button: "Download .ics" (generated server-side,
    works with any calendar, needs no OAuth).

------------------------------------------------------------------------
QR Ticketing
------------------------------------------------------------------------

  - qrcode          : generates the QR image (data URL / SVG) for display
  - html5-qrcode    : browser camera scanner on the check-in screen
  - QR payload is a random, unguessable token only (32 random bytes,
    base64url, generated with crypto.randomBytes). It contains NO personal
    data. The token is stored hashed (SHA-256) in tickets.token_hash; the
    plain token is only ever shown to its owner.

Forms, Data & Utilities

  - @tanstack/react-query : client data fetching/caching where needed
    (search results, admin tables)

  - Playwright    : end-to-end tests for the critical flows

## Data Model (Supabase PostgreSQL)
################################################################################

  All tables have RLS ENABLED. Primary keys are uuid. created_at / updated_at
  on every table. Timestamps stored in UTC, displayed in Asia/Karachi.

  profiles
    id (= auth.users.id), email, first_name, last_name, erp_number (nullable),
    account_type ('student'|'faculty'), global_role ('user'|'office'|
    'super_admin'), phone, avatar_url

  societies
    id, name, slug (unique), description, logo_url, contact_email, is_active

  society_members
    id, society_id, user_id, role ('president'|'admin'|'panel'), status
    ('active'|'removed'), added_by, unique(society_id, user_id)

  events
    id, society_id, title, description, category, venue, starts_at, ends_at,
    capacity, registration_type ('solo'|'team'), team_min, team_max,
    is_paid, price_pkr (integer, smallest unit handled in Stripe as PKR/USD
    test amount — see Stripe note), image_url, status ('draft'|'published'|
    'cancelled'|'completed'), cancellation_reason, registration_closes_at,
    created_by

  event_faculty_advisors
    id, event_id, faculty_user_id, unique(event_id, faculty_user_id)

  teams
    id, event_id, name, leader_id, created_at

  registrations
    id, event_id, user_id, team_id (nullable), status ('pending_payment'|
    'confirmed'|'cancelled'|'refunded'), unique partial index on
    (event_id, user_id) WHERE status IN ('pending_payment','confirmed')
    — enforces no duplicate active registration at database level

  tickets
    id, registration_id (unique), event_id, user_id, token_hash (unique),
    status ('active'|'void'), issued_at

  attendance
    id, ticket_id (UNIQUE), event_id, user_id, checked_in_at, checked_in_by
    — the UNIQUE(ticket_id) constraint is what guarantees one check-in per
      ticket even under simultaneous scans

  payments
    id, registration_id, stripe_checkout_session_id (unique),
    stripe_payment_intent_id, amount, currency, status ('pending'|'paid'|
    'failed'|'refunded'|'partially_refunded'), created_at

  refunds
    id, payment_id, stripe_refund_id (unique), amount, status ('pending'|
    'succeeded'|'failed'), reason

  processed_stripe_events
    stripe_event_id (primary key), type, processed_at   — webhook idempotency

  feedback
    id, event_id, user_id, rating (1–5), comment, unique(event_id, user_id)

  notifications_log
    id, user_id, event_id, type, status, provider_id, created_at

  audit_log
    id, actor_id, action, entity_type, entity_id, metadata (jsonb), created_at
    — written for event cancellation, society-admin changes, refunds,
      check-ins, publish/unpublish (NFR14)

------------------------------------------------------------------------
Critical Postgres Functions (atomic, SECURITY DEFINER, row-locked)
------------------------------------------------------------------------

  register_for_event(event_id, user_id, team_id?)
    - SELECT ... FOR UPDATE on the event row
    - Checks: event published, registration open, not cancelled, user eligible,
      no duplicate active registration, no schedule clash (see rule below),
      confirmed + pending count < capacity
    - Inserts registration (status 'confirmed' if free, 'pending_payment' if
      paid) and, for free events, the ticket
    - Capacity can NEVER be exceeded, even under bursts (NFR3)

  check_in_ticket(token_hash, event_id, scanner_id)
    - Verifies scanner is an active admin of the event's society
    - Inserts attendance row; UNIQUE(ticket_id) makes the second scan fail
      cleanly ("Already checked in at 14:32")

  cancel_event(event_id, reason, actor_id)
    - Sets status 'cancelled', voids tickets, marks registrations for refund,
      writes audit_log; refunds and emails are triggered by the route handler

------------------------------------------------------------------------
Default Business Rules (decisions taken so the build is unblocked;
each lives in one constants file and can be changed without redesign)
------------------------------------------------------------------------

  - Schedule clash        : BLOCKED. A user cannot register for an event that
                            overlaps one of their active registrations; the UI
                            names the clashing event.
  - Team size             : 2 to 5 members including the leader (per-event
                            team_min / team_max override this).
  - Team members          : must already have a RADES account; the leader adds
                            them by IBA email. Each member must accept — their
                            registration only becomes active once all members
                            are valid and (if paid) each member pays for their
                            own ticket.
  - Team edits            : the leader may edit members until registration
                            closes.
  - Event deletion        : allowed only if the event has zero registrations;
                            otherwise the admin must CANCEL it.
  - Refund policy         : full refund automatically when a paid event is
                            cancelled. No refunds for self-cancellation in the
                            prototype.
  - Self-cancellation     : a student may cancel a free registration before
                            the event starts; ticket is voided, seat released.
  - Feedback eligibility  : only users who CHECKED IN, only after ends_at.
  - Waitlist              : not implemented; "SOLD OUT" shown at capacity.
  - Highest society admin : (president) may only be replaced by the Office or
                            by the current president.
  - Registration closing  : closes at registration_closes_at or event start.

  NEXT_PUBLIC_GOOGLE_CLIENT_ID=xxxxxxxx.apps.googleusercontent.com

  Rules: only NEXT_PUBLIC_ variables reach the browser. The service-role key

  key can never be used by accident.

  person) + "TEST MODE" info badge + helper box showing the Stripe test card

  Success page (/checkout/success?session_id=...): polls the registration

  ticket. States: Processing / Confirmed / Failed / Expired — each with a clear
  next action. Cancelled page: "Payment cancelled — your seat is held until
  hh:mm" with [Try again].
  IMPORTANT: confirmation is driven by the verified webhook, never by the
  redirect URL alone.

  - Processing → Confirmed: crossfade 0.3s with tick draw animation.

################################################################################
## Global Animation Patterns
################################################################################

------------------------------------------------------------------------
Principles
------------------------------------------------------------------------

  - Simple and professional: fades, small vertical slides (<= 24px), subtle
    scale (0.96–1.05). No bounces on content, no parallax, no long delays.
  - Durations: micro-interactions 0.12–0.2s · content 0.3–0.4s · never > 0.6s.
  - Easing: easeOut for entrances, easeInOut for crossfades, one spring
    (stiffness 300, damping 30) for panels and sheets.
  - prefers-reduced-motion: a useReducedMotion() wrapper replaces transforms
    with plain opacity changes or removes animation entirely.

------------------------------------------------------------------------
Scroll-Based Entrance (default for content blocks)
------------------------------------------------------------------------

  initial    : { opacity: 0, y: 20 }
  whileInView: { opacity: 1, y: 0 }
  transition : { duration: 0.4, ease: 'easeOut' }
  viewport   : { once: true, amount: 0.15 }

------------------------------------------------------------------------
Stagger Container Pattern
------------------------------------------------------------------------

  // Parent
  variants: {
    hidden : { opacity: 0 },
    show   : { opacity: 1, transition: { staggerChildren: 0.06 } }
  }

  // Child
  variants: {
    hidden : { opacity: 0, y: 16 },
    show   : { opacity: 1, y: 0, transition: { duration: 0.35 } }
  }

------------------------------------------------------------------------
Card Hover Pattern (clickable cards only)
------------------------------------------------------------------------

  // Tailwind (colour / shadow via CSS)
  className="border border-[#E2E8F0] shadow-sm transition-shadow
             duration-200 hover:shadow-md"

  // Motion (lift)
  whileHover={{ y: -3 }}
  transition={{ duration: 0.2, ease: 'easeOut' }}

------------------------------------------------------------------------
Page Transition
------------------------------------------------------------------------

  <PageTransition> wraps page content in app/template.tsx:
    initial { opacity: 0, y: 8 } → animate { opacity: 1, y: 0 }, 0.25s.

------------------------------------------------------------------------
Feedback & State Animations
------------------------------------------------------------------------

  Loading dots  : 3 dots, scale 0.5→1→0.5, 0.15s stagger, infinite.
  Success tick  : SVG pathLength 0→1, 0.5s, followed by scale 0.96→1.
  Toast         : slide y:16→0 + opacity (sonner defaults, themed).
  Skeleton      : opacity 0.6↔1 pulse, 1.2s, solid #F1F5F9 blocks.
  Counters      : animate(0, value, { duration: 0.8, ease: 'easeOut' }).

################################################################################
## API Routes (Server-Side Business Logic)
################################################################################

  Every route: validates input with zod → authenticates via Supabase session
  → authorises role / society membership → calls the atomic Postgres function
  or external service → returns typed JSON with consistent error codes.

  POST /api/auth/signup
      Re-validate email pattern; call supabase.auth.signUp; create profile.
  POST /api/events/:id/register
      Calls register_for_event(); on free events creates ticket + sends
      confirmation and ticket emails; on paid events returns registration in
      pending_payment.
  GET  /api/tickets/:id
      Returns the ticket for its owner only; generates the QR data URL.
  POST /api/check-in
      Society admin only. Hashes the scanned token, calls check_in_ticket().
      Returns VALID | ALREADY_CHECKED_IN | INVALID | CANCELLED.
  GET  /api/analytics/events/:id
      Society admin / Office / advising faculty (read-only).
  POST /api/calendar/add
      Receives Google access token + event id; verifies the user is registered;
      calls Calendar events.insert; returns the created event link.
  GET  /api/calendar/ics/:id
      Generates an .ics file for a registered event.
  POST /api/payments/checkout
      Verifies pending_payment registration and that the seat hold is valid;
      creates a Stripe Checkout Session (metadata: registration_id,
      event_id, user_id; expires_at 15 min; success / cancel URLs); stores
      payments row (pending).
  POST /api/stripe/webhook
      Verifies Stripe signature; inserts event.id into processed_stripe_events
      (skip if exists); on checkout.session.completed → payment 'paid',
      registration 'confirmed', ticket issued, emails sent; on
      checkout.session.expired → registration cancelled, seat released; on
      refund events → update refunds / payments.
  POST /api/events/:id/cancel
      Society admin only. Runs cancel_event(), creates Stripe refunds,
      sends emails, logs audit.
  POST /api/feedback
      Verifies event ended and the user checked in; one per user per event.

  Error format: { error: { code, message } } with correct HTTP status
  (400 validation, 401 unauthenticated, 403 forbidden, 404, 409 conflict —
  duplicate / clash / sold out, 500).

################################################################################
## Security & Integrity Notes
################################################################################

  - RLS on every table. Students read only published events and their own
    registrations, tickets, payments, feedback. Society admins read / write
    only rows of their own society. Office has read-only access across
    societies. Faculty read events they advise.
  - Policies are tested with SQL tests for each role (allowed + denied).
  - The service-role key is used only inside server route handlers, never in
    client bundles.
  - Ticket tokens: 256-bit random, stored hashed, constant-time comparison.
  - Check-in and registration use row locks / unique constraints so retries,
    double-taps and simultaneous scans cannot create duplicates.
  - Webhook idempotency through processed_stripe_events and upserts keyed by
    Stripe IDs.
  - Rate limiting on sign-up / sign-in / registration endpoints (simple
    in-database counter or Vercel edge middleware, free).
  - Security headers via next.config (CSP, X-Frame-Options, Referrer-Policy);
    HTTPS enforced by Vercel.
  - Audit log for cancellations, refunds, admin changes, check-ins.
  - Passwords never handled by app code — Supabase Auth only.

################################################################################
## Performance Notes
################################################################################

  - Server components for all read-only pages; client components only for
    forms, scanner, filters and animated widgets.
  - Primary pages must load within 3 seconds on typical mobile networks
    (NFR1); target Lighthouse Performance >= 90, Accessibility >= 95.
  - Event images through next/image (WebP, sized, lazy). Upload limit 2 MB.
  - html5-qrcode and recharts are dynamically imported (next/dynamic) so they
    never load on pages that don't use them.
  - Database indexes: events(status, starts_at), events(society_id),
    registrations(event_id, status), registrations(user_id), tickets
    (token_hash), attendance(ticket_id), full-text index (GIN tsvector) on
    events title / description + society name for search.
  - Search: Postgres full-text search + ILIKE fallback, debounced 300ms.
  - Burst test: k6 script fires 300 simultaneous registrations at an event
    with capacity 100 — expected result exactly 100 confirmed, zero
    over-capacity, no duplicates; at least 200 concurrent users supported
    (NFR2, NFR3).
  - Animations use transform and opacity only.
  - Free-tier awareness: Vercel Hobby function timeouts and Supabase Free
    connection limits — use the Supabase pooled connection string for route
    handlers and keep functions short.

################################################################################
## Accessibility & Usability
################################################################################

  - All form fields have visible labels, required-field markers and
    understandable validation messages (NFR17).
  - Fully keyboard-operable navigation, dialogs (focus trap), tabs, rating
    stars and filters; visible focus ring (2px #1D4ED8 + offset).
  - Contrast >= 4.5:1 for text; status is never conveyed by colour alone
    (icon + text on every badge).
  - Alt text on informative images; decorative images aria-hidden.
  - Screen-reader announcements for scan results and toast messages
    (aria-live).
  - Semantic landmarks (header, nav, main, footer), one h1 per page.
  - Dates shown with weekday and timezone abbreviation (PKT).
