RADES — PROJECT HANDOFF

RADES is a responsive campus event platform for IBA Karachi. It supports public
event discovery, student and faculty accounts, society administration, event
approval, individual and team registration, Stripe test checkout, per-person QR
tickets, check-in, registration history, event emails, Google Calendar actions,
paid-event cancellation refunds, event analytics, and eligible post-event
feedback.

ROLES
- Student: discover events, register, manage their profile, view history and
  tickets, add events to Google Calendar, and submit eligible feedback.
- Society admin: manage society events, view event analytics, and scan/check in
  tickets for their society.
- Faculty patron: review society event submissions.
- OSSIE: manage societies and assignments, review events, and view campus-wide
  reporting.
- Super admin: development and operational administration.

PROJECT RULES
- Keep all authorization checks in server routes/actions and database policies;
  hiding a control in the UI is not access control.
- Preserve existing user accounts, passwords, and core database records. Do not
  reset credentials or modify production data as part of normal implementation.
- Stripe is test mode only. Reject live credentials and do not add raw card
  fields or store card data.
- Validate input on both client and server. Handle retries, concurrent requests,
  duplicate registrations, capacity boundaries, expired holds, repeated ticket
  scans, cancelled events, and provider failures explicitly.
- Keep user-facing errors and success messages beside the relevant action and
  expose them accessibly (status/alert semantics, keyboard operation, contrast).
- Match new or changed screens to `docs/RADES_wireframes.md` where a wireframe
  exists. Preserve the current responsive visual system where none exists.
- Use the **Ink & Parchment** palette, Georgia font stack, square corners, and
  theme-aware colors documented in `docs/RADES_wireframes.md` and implemented
  in `src/app/globals.css`. Keep light and dark modes legible; do not introduce
  unrelated colors or alter existing page layout for visual-only changes.
- Keep transactional email branding aligned with the light palette. Email logo
  URLs must be absolute and use the public RADES logo asset. Preserve its
  transparency rather than placing it on a solid tile; escape dynamic content
  and retain email-client-compatible markup.
- Do not expose secrets from `.env.local`; update `.env.example` with blank
  placeholders when configuration changes.
- Keep `docs/WORK_LOG.md` accurate about implementation, verification, and
  external dependencies. Record migrations in `supabase/MIGRATION_STATUS.md`;
  never claim a remote migration has been applied without confirmation.

DEVELOPMENT
- Use the versions and conventions already installed in this repository. Before
  changing Next.js code, read the relevant guide under
  `node_modules/next/dist/docs/` as required by `AGENTS.md`.
- Useful commands: `npm run dev`, `npm run lint`, `npm run typecheck`,
  `npm run test:e2e`, and `npm run build`. Playwright tests use isolated mock
  backend data and do not require production credentials.
- For work spanning features, use a focused branch per feature, verify it, merge
  it into the integration branch, then verify the complete integration branch.
- Do not add a test framework or test suite unless requested; run existing
  verification commands when the task calls for verification.

LOCAL CONFIGURATION
- Copy `.env.example` to `.env.local` and configure backend URL/keys before
  starting the app.
- Email delivery needs a configured application sender and identity-provider
  sender. Use `EMAIL_TEST_RECIPIENT` for development routing when appropriate.
- Paid registration and refunds need Stripe test keys plus a verified webhook.
- Calendar insertion needs a Google OAuth web client ID and the Calendar API
  enabled in Google Cloud. Add the local origin to the OAuth client.
- Never place credentials in source control, screenshots, logs, or user-facing
  responses.
